# Evo Talos SDLC Kit - Release Notes v0.11

**Release Date:** 2026-09-15

---

## Overview

v0.11 fixes a guard defect that made Claude Code's own memory facility unusable from a kit-governed project, and closes the class of false positives behind it: `orchestrator-write-guard` was adjudicating paths outside the project entirely.

Upgrade is recommended for every project running the kit, and required for anyone who has relocated `CLAUDE_CONFIG_DIR`.

---

## Major Features & Changes

### 1. `orchestrator-write-guard` is scoped to the project root

**What changed:**
- `decide()` now returns `outside-project-root` for any absolute path outside `CLAUDE_PROJECT_DIR`, evaluated before worktree detection and before ownership classification.
- Ten new hook tests cover the jurisdiction boundary, the fail-closed cases, and the in-root regressions.

**Why:**
The ownership map is a statement about paths *inside* the project, but the guard had no project-root awareness. `normalize()` only strips a leading `./` and every row matches by tail (`(^|/)docs/...`), so absolute paths anywhere on the filesystem were classified — and anything unrecognized was blocked.

Claude Code's per-user state under `$CLAUDE_CONFIG_DIR/projects/...` is not a project file, not a kit artifact, and owned by no kit role. It therefore fell through to `unrecognized-path`, and the memory facility could not write from a governed project. On a default install the path contains a `/.claude/` segment and is rescued *by accident* by the kit-internal row; relocate the config dir and the same write blocks. The bug was latent for everyone on defaults.

**Why jurisdictional rather than an ownership row:**
No portable row can be written for a per-user, env-dependent absolute path — `hooks/lib/role-ownership.cjs` is copied into every project by `sdlc-init` and shipped in the plugin, so a regex matching one machine's config layout would be wrong for every consumer. Labelling the path `shared-doc` would also assert an ownership the kit does not have. The jurisdiction check is portable, needs no per-user configuration, and clears the whole class: caches, temp, any user-global state.

**Impact:**
- The memory facility works from kit-governed projects, on default and relocated config dirs alike.
- No change to any in-project decision. `role-ownership.cjs` is untouched.
- Tools writing to user-global state stop being blocked for the wrong reason.

**Fails closed, by design:**
- `CLAUDE_PROJECT_DIR` unset → the check is skipped entirely and prior classification stands. It never falls back to `process.cwd()`, which would let any write escape by running from a different directory.
- Relative paths → skipped; they are project-relative by construction.
- Case-insensitive filesystems (macOS, Windows) → a case-folded retry before concluding "outside", so a case mismatch between the harness-supplied root and path cannot widen the guard.

### 2. Test-name honesty fix

`orch-write: allows absolute Claude memory path` asserted that the memory facility worked, but passed only because its fixture `/Users/test/.claude/projects/...` contained a `/.claude/` segment and was rescued by the kit-internal row. It tested the default layout and nothing else. Renamed to say so, with the relocated-config-dir cases beside it.

## Upgrade Notes

The guard runs from **both** copies when a project registers its own (see the phase-54 T-248 note at the top of `orchestrator-write-guard.cjs`). Updating the plugin alone does not unblock a project whose vendored `.claude/hooks/` copy predates this release — re-run `sdlc-init` or refresh that copy.
