# Evo Talos SDLC Kit - Release Notes v0.17

**Release Date:** 2026-09-18

---

## Overview

v0.17 lets a task inherit an already-confirmed design record instead of being required to duplicate it. A corrective or remediation task on a surface another task designed could not close truthfully; the only exit was an escape hatch.

---

## Major Features & Changes

### 1. `Design lineage: T-NNN` — the artifact set resolves from the task that owns the design

**What changed:**
- `ui-task-readiness-guard.cjs` reads an optional `Design lineage:` header field. When present, the four closure artifacts are resolved from that task id instead of the dispatched one.

**Why:**
T-269 corrects a payload mapping on the admin-web Legal Documents surface. `Track: fe`, `Design sub-status: design-confirmed` and a real Figma node (`47:363`) are **all true** — the guard classified it correctly, and this is NOT the contradictory-header case. But the four artifacts live under **T-248**, the task it remediates, and all four exist there. Requiring `T-269`-named copies meant authoring a second record of the same design — the duplicate the operator had already declined to fabricate (ISSUE-260) — so a truthful task had no passing state and the only remaining exit was `CLAUDE_SKIP_UI_READINESS_CHECK=1`.

**A guard must not be satisfiable only by a false assertion.** Fabricating a duplicate design record to satisfy a check is that, and reaching for a hatch because no honest input exists is the same failure seen from the operator's side.

**Declared as ONE id, not four paths:** the `## Linked artifacts` section writes them decorated (`docs/test-cases/by-task/T-248/{structural,functional}.md`), and parsing that is guesswork. One token is unambiguous. The id is read through backticks and trailing prose, because that is how task headers are written.

**Nothing is relaxed except which id names the files.** Frozen status, section rules and required rows all run against the resolved set unchanged.

**Fails closed in every direction, and the tests pin each one:**
- An inherited record that is itself incomplete **blocks**, exactly as an incomplete own record would.
- A self-referencing lineage is not a lineage — it falls back to the task's own set.
- A value with no `T-NNN` falls back too, rather than passing vacuously.
- Removing the resolution fails 4 assertions; making it unconditional fails 4 others. The narrowing is enforced from outside the implementation, not asserted in a comment.

**Self-authorization is not possible:** `docs/plan/**` is `orchestrator-only` in the ownership map, so a dispatched role cannot edit its own task file to point this anywhere. The TL or Orchestrator declares it — the same authority that created the task.

**Not chained, on purpose:** a lineage pointing at a task that itself declares one is not followed. One hop keeps the record traceable to a single origin.

### 2. The block message teaches the field, and stops misdescribing the hatch

A block with no lineage now says the field exists and what it is for — an author staring at four "missing" artifacts that demonstrably exist had no way to discover it. A block *with* a lineage names the lineage id, states that the set shown is resolved from it rather than from the task, and forbids creating `<task-id>`-named copies to satisfy it.

The hatch line also now states that `CLAUDE_SKIP_UI_READINESS_CHECK` is read from the **launch environment** — an inline `VAR=1` prefix on a tool call cannot reach a hook process. That advice was wrong in 14 places across the kit; this fixes one of them, and the rest are tracked.

---

## Upgrade Notes

Adding `Design lineage:` to a task header is optional and backward-compatible: a task without it behaves exactly as before.

The v0.11–v0.16 notes still apply: hooks run from **both** copies when a project registers its own, and enforcement is the union of every registered copy's blocks. Refresh the vendored `.claude/hooks/` copy as well as the plugin.
