# Evo Talos SDLC Kit - Release Notes v0.18

**Release Date:** 2026-09-23

---

## Overview

v0.18 removes an agent-authority restriction that left **seven of the kit's nine working roles with no legal forward transition out of the one stage they own**. A dispatch could finish its work correctly and have no honest way to say so.

---

## Major Features & Changes

### 1. `in-progress → ready-for-deploy` is no longer restricted to the dev roles

**What changed:**
- The `['in-progress→ready-for-deploy', {be-dev, fe-dev}]` entry is removed from `STRICT_AUTHORITY`. The state-machine edge itself is unchanged and still enforced.

**What it meant versus what it encoded:**
The edge means *"the dispatched role has finished its own work."* Every working role has an `in-progress` stage on its own tasks, so restricting it to the two dev roles encoded an assumption that only devs hold tasks. **`ba`, `sa`, `tl`, `qa-author`, `ui-ux-designer`, `devops` and `qa-exec` were all locked out.** Their only exits from `in-progress` were `blocked` or `failed` — both false statements — or an Orchestrator applying the transition by hand.

A full audit of the table found this is the whole of the defect: every other "stuck" pair is correct by design (`be-dev` cannot leave `ready-for-deploy` — devops deploys; `qa-author` cannot leave `in-test` — qa-exec judges).

**The rule was contradicted by its own project's history.** In the consuming project, 44 `qa`, 25 `infra`, 3 `design` and 1 `ba` task had reached `done` — and every one of them had to traverse this edge to get there. The restriction had been routed around ~70 times before it was reported.

**Why removing it costs nothing.** `plan-update.json` is written per dispatch, from that dispatch's own worktree, for its own task. No role can assert this edge on another role's behalf regardless of what the table says, so the restriction never prevented the thing its own comment described.

**What still protects the FR-022 class — unchanged:**
- `ready-for-deploy → in-test` — **devops only**: a build must actually have been deployed.
- `in-test → done` / `in-test → failed` — **qa-exec only**: QA must actually have run.

Those are the edges where a *different* gate must have executed, and they are what stop a role certifying work it did not do. A role-versus-task-type mismatch — a devops dispatch on a `be` task — is a **routing** error and belongs to `kit-role-dispatch-guard`, not to this table. Encoding it here produced only a false negative for every non-dev role.

### 2. Regression coverage

Nine new assertions: all eight working roles plus the Orchestrator proposing the edge, and one negative proving `ready-for-deploy → in-test` still refuses a non-devops agent. Restoring the old restriction fails exactly 8 of them.

---

## Known gap, NOT fixed in this release

`VALID_TRACKS` is `{be, fe, be+fe, infra, qa, ba, sa, tl}`, but consuming projects use track values outside that set — `design` and `cross-cutting` were both observed on tasks that reached `done`. Notably the kit has a `ui-ux-designer` **role** with no corresponding **track**. A plan-update carrying one of those values is rejected on schema before any authority check runs, which is the same class of defect as the one fixed above, one surface over.

This is left open deliberately: the track vocabulary is a project-level naming decision, not a kit default to widen unilaterally.

---

## Upgrade Notes

The v0.11–v0.17 notes still apply: hooks run from **both** copies when a project registers its own, and enforcement is the union of every registered copy's blocks. Refresh the vendored `.claude/hooks/` copy as well as the plugin.
