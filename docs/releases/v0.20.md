# Evo Talos SDLC Kit - Release Notes v0.20

**Release Date:** 2026-10-12

---

## Overview

v0.20 closes two guard defects that forced hand workarounds, ships a guard capability that projects had been patching locally, and adds three process rules aimed at defects that passed every existing gate. Hook fixes carry regression tests that were run against the 0.19.0 code first, to show they fail there.

---

## Fixes

### 1. `ui-task-readiness-guard`: handoff-only design lineage

`Design lineage: T-NNN` (v0.17) resolved **all four** closure artifacts from the lineage id. That fits a corrective task on another task's surface, but not the design/FE split, where the design task owns the confirmed **handoff** and the FE task produces its **own** refs, visual-spec and by-task pack. Those FE tasks false-blocked with every artifact present.

- `Design lineage: T-NNN (handoff only)` / `handoff-only` resolves the handoff from the lineage id and the other three from the task's own id. All four remain required.
- A bare `Design lineage: T-NNN` keeps full inheritance. Prose such as "the handoff is the only artifact reused" does not trigger the split.
- The no-lineage block message now advertises the handoff-only form.
- 8 new assertions; 3 fail on 0.19.0.

### 2. `orchestrator-bash-guard`: §9 Step 0.5 can run as written

Step 0.5 told the Orchestrator to `rm plan-update*.json` stragglers in the project root, and the guard refused every spelling of that command — a mandatory pre-flight step that could never run.

- The cleanup carve-out now admits project-root files matching `plan-update*.json` — root only, files only, a single uncomposed command, a glob only in the final segment, no symlinks, no mixing with other paths.
- Step 0.5 text corrected: it no longer claims to delete stragglers in subdirectories (the step is a root, non-recursive sweep), and tracked stragglers are named explicitly rather than globbed.
- 10 new assertions; 4 fail on 0.19.0.

### 3. Format boundaries the "same type" test hides

The §6 detection heuristic compares encodings, so two crossings with the same type on both sides were never flagged:

- **Width boundary** — a free-form client string persisted into a bounded column (`string` → `VARCHAR(16)`), with no `maxLength` in the contract.
- **Identity binding** — a field one service emits that another uses as a lookup key; when the binding drifts, a gate UPDATE matches zero rows and reports success.

Changes:

- `format-boundary-contracts`: both classes are boundaries by default, with rules, worked rows and declared zero-match handling.
- `architecture-validator` Step 2: explicit `width-boundary-missing` and `identity-binding-missing` checks, including walking `docs/api-contracts/` for persisted strings without `maxLength`. The report template gains both rows.
- `api-contract-author`: persisted request strings must carry a column-fitting `maxLength`.

### 4. Reopens count; diagnose before the second retry

When a code role cannot run the verification itself (operator-run build, on-device check, live probe), a failed verification reopened the task, but the circuit breaker counted only QA `failed` and dispatch errors. A build-blocker could cycle through speculative fixes indefinitely.

- `orchestrator-operating-rules.md` §9 **Step 7.6 Reopen discipline**: record each reopen; on the second reopen of the same symptom, dispatch the Debugger for a root cause cited from the failing component's source before any further fix; scope guards yield to evidence through an operator decision.
- `autonomous-loop.md` §15.6: reopens count toward the per-task failure cap.
- `task-sizing`: build-blocker sub-plans state the cause as a hypothesis and do not fence out fix classes before diagnosis.

### 5. Operator-run build handoff (Flutter)

- `flutter-platform-integration` Procedure step 7: read the failing plugin's own build files before fixing; never call a static read "verified"; the build handoff names the command, host prerequisites, a **release-signing SHA-1 check** (`apksigner verify --print-certs`), and the post-install smoke.
